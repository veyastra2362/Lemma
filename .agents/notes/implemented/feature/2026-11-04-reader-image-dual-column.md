# Agent Note: 图文双栏对照（回到最初的设计意图）

Status: implemented

## Problem

双栏窗口最初的设计是**「图文双栏对照 + 原图译文覆盖层」**（见 `docs/PLAN.md` 的窗口架构图），
但 M3 时期没有 OCR，只能退化成"纯文本双栏"——于是它既不承载图文，也不比浏览器翻译插件强多少，
定位悬空（这个质疑是使用者先提出的，不是我自己发现的）。

M4c 打通截图 OCR 之后，缺的最后一块是：**把截图和文本框坐标一起交给双栏窗口**。

## Decision

让 `ReaderPayload` 携带 `blocks`（每块带 `quad` 四点坐标）与 `image`（PNG base64），
双栏窗口据此支持两种形态：

- **并排**：左原图 + 左下 OCR 逐行文本，右侧译文；块与块 hover 联动高亮；
- **覆盖**：译文直接画在原图对应的文本框位置上（半透明底，hover 提亮）。

配套决定：

- **PNG + base64 传输**：一张 700×300 的 RGB 是 630 KB，base64 后 ~840 KB；
  编成 PNG 通常 30–200 KB。为了不引依赖，base64 编码器自己写（20 行）。
- **截图 OCR 时顺带存好图文 payload**，`open_reader` 发现"已有同文本的图文 payload"时**不覆盖**成纯文本。
- 覆盖层坐标用**百分比**换算（`quad / image.width`），这样图片被缩放时贴片仍然对齐。

## Alternatives considered

- **传原始 RGB 给前端**：不用编码，最省 CPU。否决原因：体积是 PNG 的 3–20 倍，
  一个 IPC 里塞几百 KB 甚至几 MB 的数组，序列化开销比编码还大。
- **前端直接用 blob URL / 自定义协议取图**：省掉 base64 的 33% 膨胀。否决原因：
  要么再开一个命令做二进制传输（Tauri v2 支持 `tauri::ipc::Response`，但要改通道约定），
  要么落临时文件（要管清理）。当前数据量下一次 base64 已经够快，不值得加这层复杂度。
- **覆盖模式用 canvas 绘制**：控制力更强（旋转文本也能贴）。否决原因：DOM 方案能直接复用
  已有的可点词渲染（下探栈、hover 高亮全都能用），canvas 里这些都要自己实现一遍。
- **把两种形态做成两个窗口**：隔离更干净。否决原因：用户会在两种读法之间来回切，
  两个窗口意味着两份状态与两次翻译。

## Consequences

- 收益：双栏第一次有了站得住的定位——**读截图/扫描件/PDF 时，版式和翻译同时在场**；
  覆盖模式让"原文在哪、译文就在哪"，不用左右找对应。
- 代价 1：IPC 单次最多带几百 KB 的 base64；超大截图（4K 全屏）会明显变慢，需要限制框选尺寸或降采样。
- 代价 2：覆盖层假设文本框是轴对齐的（用 min/max 求包围盒），**旋转文本的贴片会歪**。
- 代价 3：图片被缩小时，覆盖层的字号不跟着缩放，长句可能超出框。
- 遗留：覆盖模式不做自动避让（译文比原框长时会盖住旁边的内容）；没有"只显示译文/只显示原文"的切换。

## Testing

真机端到端（双重冒烟：`LEMMA_REGION_SMOKE` + `LEMMA_REGION_SMOKE_READER`）：

```
region smoke ok chars=22 text= GenP Guides - / 抖音精选 / 精选
region smoke reader opened
translate ok chars=13 / chars=4 / chars=2
```

截图确认：
- **并排**：左原图（Chrome 标签页 + 抖音图标）+ OCR 逐行文本，右侧译文三段对齐；
- **覆盖**：`GenP 指南` 精确盖住 "GenP Guides"、`Douyin Featured` 盖住「抖音精选」、`Featured` 盖住「精选」。

顺带修掉一个真实 bug：**标题栏整块挂了 `data-tauri-drag-region` 会把按钮点击吞掉**
（双栏的「并排/覆盖」切换点不动就是这个原因）。改成只有标题文字可拖拽。
