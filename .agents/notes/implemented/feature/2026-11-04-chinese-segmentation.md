# Agent Note: 中文分词（CC-CEDICT + 逆向最大匹配）

Status: implemented

## Problem

UIA 的 `TextUnit_Word` 对中日韩文本只在标点/空白处断词。实测两种失败形态：

- 光标停在一个字上 → 拿到单字（`第`）；
- 拿到一整段（`当前进度：`），尾随标点还跟着走。

词库是英→中，所以**中文取词几乎只能得到"未收录"**——一条完全用不上的路径。

## Decision

用 **CC-CEDICT**（12.5 万条，词条自带拼音 + 英文释义）做两件事：中文词表与中文释义；
分词用**逆向最大匹配（RMM）**。取词时：

- 文本含汉字且**不需要翻译**（短文本）→ 用词表切分；
- 切出 1 个词 → 直接查该词的中文词条；
- 切出多个词 → **不猜用户想查哪个**，把候选列成 chips 让他点；
- 切不出（或本来就是长句）→ 原样走原来的翻译路径。

配套：
- 词表存进 redb 的独立表 `zhTerms`（与英文 `terms` 并存，互不覆盖；`--import-cedict` 追加而不重建）；
- 分词器**懒加载**：第一次遇到中文取词才读词表（约 4–5 MB 结构 + redb 页缓存）；
- 新增无头命令 `--segment <text>`，用来在抢不到窗口焦点时验证分词。

## Alternatives considered

- **jieba 词频表 + 最短路径 DP**：最强的理由是准确率——有词频才能选"更可能的切分"，对歧义串明显更准。否决原因：要再引一份 5 MB 数据源、多一次导入、多一份常驻内存；而 CC-CEDICT 的 12 万词条已覆盖绝大多数阅读场景，RMM 在真实句子上给出的结果（`人工智能/助手/正在/阅读/深度/内容`）已经可用。若后续发现歧义切分明显出错，再换成 DP。
- **`HashSet<String>` 存词表**：实现最直观、查找 O(1)。否决原因：实测让进程多占约 33 MB（121k 项，每项都有独立堆分配与哈希表开销）。改成**排序 `Vec` + 二分查找**后同样等价，结构内存降到 4–5 MB。
- **只用 ISO 单字切分**：最省事，但中文单字几乎没有检索价值（"服"和"服务"不是一回事）。否决。
- **梗概阶段就不做中文**：理由是用户主阅读语言看起来是英文。否决原因：这是产品在国内阅读场景的硬门槛，晚做不如早做；而且分词器是懒加载，英文用户零成本。

## Consequences

- 收益：中文取词从"完全不可用"变成"可用"——能切词、能查、能点候选下探。
- 代价 1：**词表加载会多占约 28 MB 工作集**（词表结构 4–5 MB + redb 中文表页缓存）。实测 CLI 峰值 7.4 → 35.7 MB。
  已记入 `docs/PERF.md` §3.4，优化方向（另存 `zh-words.txt` 顺序读）列入 `docs/TODO.md`。
- 代价 2：RMM 对歧义串不如词频 DP，可能出现 "研究生命科学" 这类切分偏差。
- 代价 3：拼音保留 CC-CEDICT 原始写法（`ni3 hao3`），没有转成声调符号；转写需要查表，收益不大。
- 代价 4：只取简体作键，繁体词条被丢弃（阅读里几乎只见简体，但港澳台用户会失手）。
- 遗留：CJK 取词没有"光标在哪个字"的信息，所以只能给候选列表而不能自动定位到光标那个词。

## Testing

- `cargo test`：78 项通过，含 `segment::tests` 10 项——两词短语、RMM 取长、标点不并入词、
  未收录汉字退化单字、中英混排保序、最长词优先、空输入。
- 无头实测：
  ```
  lemma.exe --segment "当前进度：多服务商"
  → [当前] [进度] ： [多] [服务] [商]    （词表 121594，最长词 19 字，76 ms）
  lemma.exe --segment "人工智能助手正在阅读深度内容"
  → [人工智能] [助手] [正在] [阅读] [深度] [内容]
  ```
- 内存：`--lookup` 峰值 7.4 MB / `--segment` 峰值 35.7 MB（同一 exe，差值即分词器成本）。
