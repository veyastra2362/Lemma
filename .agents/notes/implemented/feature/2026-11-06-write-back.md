# Agent Note: 原地回填（M6）

Status: implemented

## 问题

读完一段外文，译文只在浮层里；想「就在原文位置读译文」就得自己去复制粘贴。
M6 要把它变成一次点击：选中 → 浮层 → 点「回填」→ 原文位置变成译文。

## 决定

**只支持原生编辑控件**（`Edit` / `RichEdit` / `Scintilla` / `TextArea` 类名）：
向控件句柄发 `EM_REPLACESEL`，`wParam = TRUE` 让它进控件自己的撤销栈。

**浏览器不提供回填**，界面上直接不出现按钮（取词时用 `can_replace()` 预判并写进 `Capture`）。

曾经实现过「剪贴板 + 模拟 Ctrl+V」兜底，实测后**整体删除**，理由见下面的备选方案。

配套的保险：

- **焦点拿不回来就取消**。`focus()` 先试 `SetForegroundWindow`，失败再试「最小化→还原」；
  两者都失败时**不粘贴**，返回「无法把焦点还给原窗口，已取消回填」。
- **撤回**：记住 `(source, control, 原文, 写进去的译文)`，再走同一条路径把原文写回。

## 依据（都是实测，不是推断）

| 目标 | 光标处元素 | Value | 结论 |
| --- | --- | --- | --- |
| 记事本 | RichEditD2DPT 文档 | 可写 | ✅ `ET_REPLACESEL` 可用，实测写入成功 |
| Chrome | 文档 | **只读** | ❌ 只能粘贴 |
| Firefox | 顶层窗口（无文档元素） | 只读 | ❌ 连控件都拿不到，只能粘贴 |

`ITextRangeProvider` **没有 SetText**，所以「UIA 直接改文本」对浏览器这条路根本不存在。

焦点一条尤其重要：后台进程调 `SetForegroundWindow` 返回 False（实测焦点仍停在微信）；
「最小化 → 还原 → 再 SetForegroundWindow」才被系统认可。测试期间有一次焦点没抢到，
译文被**粘贴到了微信窗口**——正因如此才把「焦点未确认就取消」写成硬约束。

## 备选方案

**剪贴板 + 模拟 Ctrl+V 兜底**（已实现过，已删除）。它看起来能覆盖浏览器，实测两个问题
无法接受：① 焦点抢不回来时会把译文**粘到别的应用里**（测试中真的粘进了微信窗口）；
② 粘贴后若目标应用自己改剪贴板，还原会失败，用户的剪贴板内容丢失。
用户明确要求"回填失败不要复制粘贴"，因此彻底删掉，只保留可校验、可撤销的原生路径。

**浏览器扩展**。真要改网页内容，只能在浏览器内部做（内容脚本改 DOM）。
那是一个独立的交付形态（Chrome/Firefox 各一份清单、各一套发布流程），
与桌面应用是两个产品面，不在本次范围。

**模拟键盘逐字输入**（`SendInput` 打字符）。能绕开剪贴板，但长句要几百毫秒到几秒，
输入法状态一变结果就乱，中文还可能被输入法劫持。

## 后果

- 剪贴板路径有**不可完全消除的风险**：目标应用可能在 `Ctrl+V` 之后自己改剪贴板，
  导致还原不完整（目前已记录日志并只在序号未变时还原）。
- 粘贴路径**无法校验**是否真的写进去了（浏览器文档读不回来），所以结果里
  `verified` 为空时前端提示「已粘贴，未能校验」，不谎报成功。
- OCR 卡片不提供回填：屏幕区域没有可写的文本控件。
- 撤回依赖「路径可重放」：原生控件可 `Ctrl+Z`；粘贴路径是「把原文再写一次」，
  如果用户在此期间自己改过内容，撤回会覆盖，风险由用户点按钮承担。
