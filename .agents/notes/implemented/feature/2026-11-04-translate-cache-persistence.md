# Agent Note: 翻译缓存落盘（重启后重复段落零成本）

Status: implemented

## Problem

译文缓存原来只在内存里（LRU 256 条），**重启就没了**。而实际阅读里"同一段话反复看"
非常常见——返回上一段、重开同一篇文章、连续框选相邻区域。每次都重新打一次网络，
既是 1–2 秒的等待，也是白打的请求。

## Decision

用 **JSON Lines 追加写**落盘到 `%APPDATA%\dev.lunar.lemma\translate-cache.jsonl`：

- 启动时读回最近 256 条塞进内存 LRU（`restore_cache`）；
- 每次成功翻译追加一行（`append`），**命中内存缓存不追加**（避免重复膨胀）；
- 文件超过 2 MB 就按"保留最近 256 条"重写一遍（`rewrite`）；
- 设置里换 provider / 目标语言时 `clear_cache()` 会**连带删文件**——
  否则重启后旧语言的译文会被读回来。
- CLI `--translate` 也 attach 同一个文件，保证两条路径行为一致。

## Alternatives considered

- **塞进现有 redb 词库**（多一张表）：不用新文件、不新增锁。否决原因：
  redb 是**独占锁**，词库已经因此让 CLI 与 GUI 打过一次架（`Database already open`）；
  而且译文写的频率远高于词库（只读），混在一起会让"删缓存"变成"动词库"，
  风险与收益不成比例。
- **单独一个小 redb**：结构化、有事务、能按 key 精确删。否决原因：
  又多了一个锁文件、又要处理 schema 版本；而缓存本来就可以整体丢弃，
  事务能力在这里是负担。JSONL 出问题直接 `head` 看、删掉即清空。
- **只在进程退出时整批写**：写得更整齐、文件不会有多余行。否决原因：
  应用被强杀（任务管理器、崩溃）就全丢，而这恰恰是最需要缓存的时候。
- **不设上限，永久累积**：实现最省事。否决原因：阅读量大时文件会无限涨，
  启动时读回的时间也随之变长；256 条足够覆盖"当天读的同一批文章"。

## Consequences

- 收益：跨进程命中实测两次运行——首次 `google · 1355 ms`，第二次
  `translate cache restored 1 entries` → **`来源：cache · 0 ms`**。
- 代价 1：文件是人可读的明文（含原文与译文），**属于隐私面**。已放在应用数据目录，
  不进仓库；但这是"落盘"必然带来的暴露面，写在这里备案。
- 代价 2：坏行（进程被杀时最后一行只写一半）靠"解析失败就跳过"兜住，不是原子写。
- 代价 3：容量上限是固定条数而非按体积/时间淘汰，长期高频使用会有"想要的旧条目被挤掉"的情况。
- 代价 4：`restore_cache` 在启动路径上同步读文件；2 MB 上限下实测可忽略，但没有单独计时。

## Testing

- `cargo test translate_cache`：4 项——追加/读回往返、坏行跳过、缺文件返回空、
  超容量只保留最近 256 条。
- 端到端（两次独立进程）：
  ```
  第一次：来源：google · 1355 ms        → 缓存行数: 1
  第二次：translate cache restored 1 entries
          来源：cache · 0 ms（缓存）
  ```
