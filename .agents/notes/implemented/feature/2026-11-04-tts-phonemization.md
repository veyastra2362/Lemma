# Agent Note: 离线朗读的音素化方案（M5a）

Status: implemented

## Problem

M5（离线朗读）卡在一个非模型问题上：**Kokoro 的 `input_ids` 吃的是音素，不是文字。**
中文这一层成熟实现都在 Python 侧（misaki / pypinyin）。

三条候选路各有硬伤：
- 自建映射表：要自己维护，多音字难；
- espeak-ng：GPL，会传染本项目的 MIT；
- Python sidecar：多一个运行时，包体与启动都变重。

`docs/TODO.md` #20 记的就是"不定这个，Kokoro 跑得再快也念不出中文"。

## Decision

**纯 Rust 自建音素化，数据源全部是已有资产**：

1. **拼音来自 CC-CEDICT**：12 万条中文词条本来就带拼音（`杜甫 [du4 fu3]`），
   已经导进 redb 的 `zhTerms` 表（`DictStore::get_zh`）。**不需要新词库。**
2. **拼音 → 注音（Bopomofo）自己实现**（`core/tts/phonemize.rs`）：21 声母 + 37 韵母 + 声调数字的确定性映射。
   实测 Kokoro 的 zh 词表正是注音体系（172 个符号里含 ㄅㄆㄇ…ㄭ 与数字 1–5）。
3. **按词查拼音，不按字**：先用已有的 CC-CEDICT 分词器切词再查，
   查不到才退到单字——见下面"踩到的第一个真错"。
4. 音色用 `voices/zf_001.bin`（[510, 256] f32，按 token 数取行）。

## Alternatives considered

- **espeak-ng 做音素化**：现成、语言多、一条命令出音素。否决原因有两条：
  GPL 与本项目的 MIT 不兼容（动态加载的法律边界也有争议）；且 espeak 的中文质量明显不如基于拼音的方案。
- **Python sidecar（misaki）**：跑通最快，与官方实现完全一致。否决原因：多一个运行时，
  安装包要带 Python 或 PyInstaller 产物（几十 MB），启动也要等解释器。
  这个产品现在的安装包只有 1.2 MiB 级，加 Python 是数量级的变化。
- **直接内嵌 misaki 的映射表（JSON）**：比自写映射省事，且与官方一致。否决原因：
  要连带移植它的分词与多音字消歧逻辑（它依赖 pypinyin 的词典），
  等于把 Python 的数据与算法都搬过来，收益不如直接用我们已有的 CC-CEDICT 分词 + 拼音。
- **跳过音素化，改用支持中文文本直入的 TTS 模型**：能省掉这一层。否决原因：
  可选的本地中文 TTS（如 CosyVoice / GPT-SoVITS）模型体积比 Kokoro 大一个数量级，
  与"主进程内存口径 30–60 MB、TTS 隔离进程"的约束冲突。

## Consequences

- 收益：TTS 的前置阻塞清掉了，整条链路纯 Rust、无新增数据源、许可干净。
  `lemma.exe --tts "深度阅读需要把原文和译文放在一起" out.wav` 已能合成出语音。
- 代价 1：**多音字靠词级查词消歧，不是靠上下文**。切词错了读音就错（`读` 在"阅读"里对，
  单独出现时取词条第一条 = `dou4`）。这是"不引入 pypinyin"的必然代价。
- 代价 2：拼音里的儿化、轻声、变调（一/不）都没有处理。
- **代价 2b（用户试听后确认 → 已修）**：能听懂，但"一个字一个字念"、缺乏连贯性。
  根因确认：我原来**逐音节加空格**，等于把每个字当成独立的词。
  查 misaki 源码（`misaki/zh.py`）确认官方是 `' '.join(word2ipa(w) for w in words)`——
  **词内音节直接相连、词间才留空格**，韵律由词边界 + 标点驱动。
  改法：分词后按词拼接、标点单独成段（`，`→`,`、`。`→`.`）。
  三种策略可用 `LEMMA_TTS_SPACING=word|syllable|none` 试听对比，默认 `word`。
- 代价 3：**RTF 实测 1.07–1.32×**（q8 量化模型，4 线程），即合成比实时慢。
  跟读场景能勉强跟上，但首句延迟明显（会话创建 ~1.2 s + 合成）。
- 代价 4（**已量化并缓解**）：在**主进程内**加载 TTS 模型，实测 RSS 从 **30 MB 涨到 332 MB**（探针估的 242 MB 偏乐观）。
  缓解办法：合成完立刻 `release_model()` 卸掉会话，实测 **332 → 71 MB**（残留约 41 MB 是 ort 分配器保留，不还）。
  设置里可改为常驻（`tts_keep_loaded`，省掉每次约 1.2 s 加载，代价是一直占内存）。
  **真正的解法仍是进程隔离**（`docs/TODO.md` #21）——现在这套只是让"用一次"的代价可接受。

## 踩到的两个真错（都是自测抓出来的）

1. **`xu1` 被念成 ㄒㄨ**：拼音规则里 j/q/x 后面的 `u` 实际是 `ü`（ㄩ），
   原实现只处理了 `un`→`ün`，漏了 `u`/`ue`/`uan`。已补规则并加单测。
2. **`读` 取到 `dou4`**：按字查 CC-CEDICT 拿的是词条第一条（"句读"的读音）。
   改成先分词、按词查拼音后变成 `du2`。**调试输出与实际合成曾走两条不同的路**
   （调试那份是另写的按字逻辑），一度让我以为改坏了——现在两者共用 `phonemes_for_text`。

## Testing

- `cargo test tts`：11 项通过——声母韵母基本映射、ㄭ（zhi/chi/shi/ri/zi/ci/si）、
  零声母、缩写还原（iu/ui/un）、`ü` 的三种写法（u:/v/ü）、j/q/x 的 ü 规则、
  无声调按轻声、**映射表产出的符号必须都在 Kokoro 词表内**、WAV 头与时长。
- 主进程内实测（`LEMMA_SPEAK_SMOKE`）：
  ```
  tts model released
  speak smoke audio=3.78s total=5788ms rss 30→332MB(峰值)→71MB(卸载后)
  ```
- 端到端（本机）：
  ```
  lemma.exe --tts "深度阅读需要把原文和译文放在一起" out.wav
  音素：ㄕㄣ1 ㄉㄨ4 ㄩㄝ4 ㄉㄨ2 ㄒㄩ1 ㄧㄠ4 ㄅㄚ3 ㄩㄢ2 ㄨㄣ2 ㄏㄜ2 ㄧ4 ㄨㄣ2 ㄈㄤ4 ㄗㄞ4 ㄧ1 ㄑㄧ3
  合成 3.53s 音频，平均用时 4377 ms（RTF 1.24x），峰值 0.300
  ```
  逐字核对：深ㄕㄣ1 度ㄉㄨ4 阅ㄩㄝ4 读ㄉㄨ2 需ㄒㄩ1 要ㄧㄠ4 把ㄅㄚ3 原ㄩㄢ2 文ㄨㄣ2 和ㄏㄜ2 译ㄧ4 文ㄨㄣ2 放ㄈㄤ4 在ㄗㄞ4 一ㄧ1 起ㄑㄧ3 —— 全对。
- 音频客观特征（我听不到，只能查结构）：RMS 0.058、峰值 0.35、71 帧里 40 帧有声 19 帧静音，
  能量曲线有明显音节起伏与停顿（`......##-....##--#####-##-####`），不像噪声或静音。
  **音质最终必须由人耳判断**，这一条我没法自己验证。
