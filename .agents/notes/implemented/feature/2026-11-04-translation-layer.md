# Agent Note: 翻译层落地（分级路由 + 语义缓存 + HUD 内联译文）

Status: implemented

## Problem

M2 结束时，单词能查（词库 2 µs），但**句子/段落只能得到「词库未收录」**。而深度阅读里真正的痛点是长句和段落——一句读不懂，逐个词查完还是不懂。缺翻译，整套系统就还是个词典。

约束有三条，互相拉扯：

1. **必须零配置可用**：自己用没问题，但要能直接跑起来就不能强制用户先去申请 API Key；
2. **不能拖慢 HUD**：HUD 首帧 SLO 是 80 ms，而网络翻译实测 0.9–2.2 s，差两个数量级；
3. **必须能换**：免密接口是非官方端点，随时可能失效，得有一个"质量优先"的替换档。

## Decision

`core::translate` 做三级结构，缓存压在路由之前。

**路由**

| 档 | 何时用 | 实测 |
| --- | --- | --- |
| 本地词典 | 单个词（`is_single_word`） | 2 µs |
| Google gtx（免密） | 句子/段落，默认档 | 0.9–1.6 s |
| OpenAI 兼容接口 | 用户在设置里切过去 | 取决于服务 |

**关键设计**

- **`is_single_word` 放在 Rust 一侧**，结果随 `Capture.needs_translation` 传给前端。判定规则只有一份实现（含单测：`hello world` / `当前进度：多服务商` / `don't` / 超长串）。
- **翻译异步、不阻塞首帧**：取词 → 立刻显示 HUD（~20 ms）→ 卡片先显示「翻译中…」→ 结果回来再填。绝不能在 capture 的同步路径里等网络。
- **缓存键 = `目标语言 + 原文`**，进程内 LRU 256 条；命中时 `provider` 标 `cache`、`elapsed_ms` 归零，前端能一眼看出是不是缓存。
- **换 provider 或目标语言时清缓存**（`update_settings` 里判断），否则会拿到另一种语言的旧译文。
- **响应解析抽成纯函数**（`google::parse_response` / `openai::parse_response`），单测覆盖分段拼接、空译文、错误体。

## Alternatives considered

- **只做 OpenAI 兼容接口**：最强理由是质量与可控性——翻译质量明显高于免密端点，还能顺手支持本地 llama.cpp，且接口稳定不容易失效。否决原因：**"先填 Key 才能用"直接违背"跑通整套"**。第一版必须打开就能译，否则用户会以为功能坏了。
- **只做免密 Google gtx**：最省事，一个 provider 一条路径。否决原因：它是非官方端点，没有 SLA，随时可能改协议或封 IP；没有第二档就没有退路，而且专业阅读场景下质量也确实不够。
- **纯本地小模型离线翻译**：最符合"端侧离线"的叙事，零网络、零隐私顾虑。否决原因：M3 阶段不划算——中文小模型要带几百 MB 权重、还要处理推理后端与量化，而翻译是**单句短文本**场景，小模型质量明显不如在线端点；离线翻译更适合放到 M5 之后单独立项。
- **在 `capture()` 里同步翻译**：实现最简单，一次调用拿到全部结果。否决原因：会把 HUD 呼出从 20 ms 拖到 1–2 s，直接毁掉"瞬态即用即走"的体验——这是整个产品的立身之本。
- **翻译结果存进 redb 持久化**：重启后仍能命中。否决原因：redb 是独占锁，GUID 进程与 CLI 已为此打过一次架；翻译缓存价值随语境衰减快，进程内 LRU 足够，持久化留到有真实命中率数据再说。

## Consequences

- 收益：整句/整段选中即可得到译文，"读不懂"这条主路通了；provider 可换；缓存让重复段落几乎零成本。
- 代价 1：**依赖网络**。断网或接口失效时，句子档直接退化到「翻译失败」——词典档仍可用。这是"零配置"换来的必然代价。
- 代价 2：免密端点**非官方**，协议可能变；`parse_response` 已做成纯函数并有坏响应单测，改协议时只需换解析。
- 代价 3：API Key 明文存 `settings.json`（本机个人工具可接受；公开分发需改 Windows 凭据管理器，已记入 `docs/TODO.md` #12）。
- 代价 4：缓存不持久化，重启后首句仍要等一次网络（连接本身已由预热解决，见下）。
- **连接预热**：启动后 1.5s 后台打一次极小请求（`translate::warm_up`），把 DNS + TLS 握手的
  约 3 秒成本从用户第一次翻译挪走。实测首次调用从 4.3 s 降到 1 s 量级（启动日志 `translate warmup ok 736ms`）。
  **只对免密 provider 做**：OpenAI 兼容接口按 token 计费，替用户发无意义请求不合适；
  且预热直接调 provider、不走 `translate()`，避免污染缓存。
- 遗留：**双栏对照窗口**未做（M3 剩余项，见 `docs/TODO.md` #2）；段落级对齐也未做，多段选中现在整段送翻译。

## Testing

- `cargo test`：67 项通过，含 `translate::tests` 12 项——`is_single_word` 边界、Google 分段拼接、坏响应、OpenAI 错误体、缓存命中与容量淘汰、缓存键按目标语言区分。
- 无头验证（不依赖窗口焦点）：
  ```
  lemma.exe --translate "The threshold value matters. But the constraint is subtler!"
  → 阈值很重要。但这个约束更加微妙！  （google · 916 ms）
  ```
  中译英、长段均实测通过；GET 比 POST form 快约 30%，已改为 GET。
- HUD 内联译文（加载态 → 结果态）需在桌面端点选句子验证——自动化脚本抢不到前台焦点。
