# Agent Note: 小字号/低对比度文本"完全识别不出来"——过滤用错了框

Status: implemented

## Problem

给基准集补了三个更难的真实场景（深色 UI 低对比度白字、12–14 px 小字、低对比度中文），
结果**三张全部 CER 1.000、段=0**——一个字都没认出来。

这在产品里很致命：**框选一小块文字是常态**，而小块里的字往往就是小的。

## Decision

把后处理的尺寸过滤从"收缩核尺寸"改成"**外扩后的框尺寸**"，即先 `unclip` 再判断。

`postprocess.rs` 原来的顺序是：

```
min_area_rect → 按 (width_edge < 8 || height_edge < 6) 过滤 → unclip → 产出候选
```

DB 输出的是**收缩核**：12 px 的字，核只有 **4.4 px 高**，直接被 `height < 6` 丢掉。
而真正喂给 rec 的是外扩后的框（同一条实测 17.3 px 高），判断就该用它。

## Alternatives considered

- **放大输入图**（我当时的第一反应）：`aligned_size` 加"长边小于 640 就放大"。
  实测确实让三张失败的图变成 CER 0.000——**但这是假因果**：真正起作用的是我同批改的过滤顺序；
  关掉放大、只留顺序修复后，三张仍然 0.000，而且放大让 `dark-zh-28`（488 px 宽）
  被切成两段、CER 从 0 退到 0.125。**已回退**，`det` 保持只缩不放。
- **降低过滤阈值**（比如 height < 2）：能过掉这一个用例，但阈值本身失去意义，
  细线、分隔线、表格线会一起进来。
- **按字号动态调阈值**：需要先知道字号，而字号正是我们要检测的东西——循环依赖。
- **不用尺寸过滤、只靠 `min_area`**：噪声框会明显变多（实测 `dark-tiny` 的连通域里就有一个 1 像素的杂点）。

## Consequences

- 收益：小字、低对比度、中文低对比度三类样本从 **1.000 → 0.000**；
  基准集整体平均 CER **0.229 → 0.004**（内容层面 0.000）。
- 代价：过滤条件作用在外扩后的框上，意味着**外扩比**会影响"什么算太小"——
  以后调 `unclip_ratio` 会连带改变过滤灵敏度，这是一处隐含耦合，写在这里备查。
- 教训：**用了环境变量做单点验证，不代表找到了因果**。这次的"放大有效"是
  同一批改动里的另一处修复在起作用；只有回退对照才能分辨。

## Testing

- 新增三个困难样本进 `tools/ocr-bench/`：`dark-lowcontrast-14`、`dark-tiny-12`、`dark-zh-lowcontrast`。
- 全量基准（12 张）：平均 **CER 0.004 / 内容 0.000**，耗时 81 ms/张。
- 回归保护：长行图（1200×300 三行 36pt）三行仍全对——确认没有把"宽行单段"搞坏。
- 调试开关：`LEMMA_OCR_DEBUG=1` 会打印 det 输入/输出尺寸与概率图统计、
  每个连通域的 `kernel WxH → expanded WxH`、以及每段的宽高比与空格帧数。
