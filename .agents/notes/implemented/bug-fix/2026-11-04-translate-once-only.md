# Agent Note: 句卡片「只有第一次翻译」——用会被重置的 id 做去重

Status: implemented

## Problem

M3 上线后实测：句子取词第一次能看到译文，之后每次呼出 HUD 都只有原文，连「翻译中…」都不出现——像是翻译功能根本没被调用。

日志里只有 `capture` 和 `hud present`，没有任何翻译痕迹，说明请求压根没发出去。

## Decision

去掉「按卡片 id 去重」的判断，改为只认状态机：`translation.status === "idle"` 才发起翻译。

- 判定抽成纯函数 `shouldTranslate(card)`，放在 `store/useDeckStore.ts`，并在 `ShellView` 里当类型守卫用（同时让 TS 确认 `original` 非空）。
- 配 7 条回归测试，其中一条直接钉住这次的场景：**连续三次 `reset`，每次都必须重新可翻译**。
- 顺带修了同批暴露的另一处漏改：`i18n.appName` 还是 `Trans`（改名时漏了这个文件），HUD 标题一直显示旧名。

## Alternatives considered

- **保留 id 去重，把 id 改成全局递增**：改动最小，只需让 `reset` 不复位 `nextId`。否决原因：这只是把症状按下去——真正的问题是「用可变标识做幂等判断」，任何一次 reset/复用都会再踩；状态机本来就表达了"这张卡还没翻译过"。
- **用原文文本做去重**（记录上一次翻译过的字符串）：能挡住重复请求。否决原因：同一句话在两次呼出里都要译（用户可能就是想再看一次），按文本去重会误杀；而且文本长度无上限，做成 key 还要额外注意内存。
- **在 Rust 侧去重**：命令层记住最近一次请求。否决原因：前端每次都会建新卡片并显示 loading，Rust 若去重会出现"卡片永远停在加载中"；职责也错位——"这张卡要不要翻译"是 UI 状态问题。

## Consequences

- 收益：每次呼出都会重新翻译，符合直觉；判定变成可单测的纯函数，回归有测试兜底。
- 代价：同一句话在短期内多次呼出会重复打网络（进程内 LRU 会在第二次命中缓存，所以实际只多一次内存查表）。
- 教训（写进代码注释）：**卡片 id 在每次 `reset` 后都从 0 开始**，任何拿它当"跨会话唯一标识"的写法都是错的。

## Testing

- `pnpm test`：20 项通过，含 `useDeckStore.test.ts` 的 7 项，覆盖
  「句子建句卡并入队翻译」「词卡不翻译」「loading/done 不重复发起」「连续三次 reset 都重新发起」「退层到底返回 false」「面包屑跳回丢深层」。
- `pnpm typecheck`：`shouldTranslate` 作为类型守卫后，`ShellView` 不再需要非空断言。
- 真机验证：设置切到「只用选区」后，在 Chrome 连续选中句子双击 Ctrl 三四次，每次都出现「翻译中…」并出译文。
