# Agent Note: HUD 在多屏下会被钳到屏顶（定位用了过期尺寸）

Status: implemented

## Problem

多屏实测：光标在副屏中间（`3500,600`），HUD 却出现在**屏幕顶部** `y=95`，
而不是光标下方。

根因：`reposition()` 在**内容渲染之前**执行，此时 `window.outer_size()` 还是**上一屏的高度**。
如果上一次内容是长句（窗口被内容撑到 400+ px），按这个高度往光标下方放会溢出工作区底部，
于是 placement 翻到光标**上方**；上方也放不下，最后被钳到工作区顶部。
等新内容变矮（比如只有 132 px），位置就停在顶部不回来了。

## Decision

记住**最近一次由内容驱动的真实高度**（`LAST_HUD_HEIGHT`，前端调 `resize_hud` 时写入），
定位时优先用它，拿不到才退回 `outer_size()`。

仍然**只做定位、不重新锚定**：`resize_hud` 里的作用域保持不变——
用户点卡片时鼠标正在 HUD 上，重新锚定会让窗口每点一次往右下挪一次（这是更早踩过的坑）。

## Alternatives considered

- **等首帧渲染完再定位**：能拿到准确高度。否决原因：那会在屏幕上"先出现在旧位置、再跳一下"，
  比现在的高估更难看；HUD 的价值就是"瞬间出现在光标旁"。
- **固定 HUD 高度、内容内部滚动**：定位一次到位，最简单。否决原因：短句只有一行时
  420×480 的空窗口很怪，也违背"内容自适应高度"这个已经确定的交互。
- **定位后再按新高度重新钳制**：看起来能修正。否决原因：内容变矮时窗口会往左上"回弹"，
  用户正在读的那几行会跳动；而内容变高时又需要重新翻转，来回抖动。
- **在 placement 里预留最大高度**：宁可放远一点也不越界。否决原因：短句时代价是
  HUD 离光标很远，违反"贴着光标"的直觉。

## Consequences

- 收益：多屏下 HUD 不再被钳到屏顶；单屏近边缘时也能正确左翻（实测 `(2047,600) → 1616,611`）。
- 代价：高度是"上一屏的"预测值，内容长度剧烈变化时（一行 → 十行）仍会偏一点；
  这是"不闪烁"换来的，可接受。
- 教训：**任何依赖窗口尺寸的定位，都要问一句"这个尺寸是哪一帧的"**。

## Testing

- 单屏近右边缘：光标 `(2047,600)` → HUD `(1616,611)` 高 132（左翻 + 高度用真实内容值）。
- 多屏（副屏 `2560,95`）：修复前 HUD 被钳到 `y=95`；修复后的复测**待副屏接回后再做**
  （当前机器只剩一块屏）。
- 门禁：`cargo clippy -D warnings` / `cargo test`（121 项）全过。
