# Agent Note: 把 TTS 赶出主进程（子进程隔离）

Status: proposed

## Problem

朗读功能已经能用，但代价是主进程内存：实测加载 Kokoro 中文 q8 模型后 **RSS 30 → 332 MB**，
即使用完就卸，峰值仍然存在，且卸载后有约 41 MB 不还给系统（`ort` 分配器保留）。

项目口径是主进程常驻 **30–60 MB**（`docs/PERF.md`）。332 MB 是它的 5–10 倍，
这个数字不是"优化一下"能解决的——它是模型权重的物理大小。

三种共享同一处逻辑的问题：
1. 峰值内存出现在用户没有任何朗读行为的时候（只要点了朗读就付）；
2. 崩溃/泄漏会带倒整个应用（TTS 是纯增量功能，不该有这个权力）；
3. 无法在空闲时真正释放（`drop` 之后 allocator 不归还）。

## Proposal

**把 TTS 跑在同一个 exe 的子进程模式里**（`lemma.exe --tts-worker`），主进程只负责：

1. **按需拉起**：第一次朗读时 `Command::new(current_exe).arg("--tts-worker")`，
   stdin/stdout 用管道；
2. **一次一个请求**：主进程写一行 JSON（`{"text": "...", "speed": 1.0}`），
   worker 合成后返回一行 JSON（`{"path": "...wav", "durationSecs": 3.8}`）；
3. **空闲即退**：worker 在 N 秒（建议 60）没有新请求就自行退出；
   主进程下次朗读时重新拉起（代价是重新加载模型约 1.2 s，与现在"用完就卸"相当）；
4. 主进程拿到 WAV 路径后用现有的 `PlaySound` 播放（播放留在主进程，因为它是毫秒级操作）。

同一 exe 而不是单独二进制：避免安装包多一个文件、避免版本漂移。

## Alternatives considered

- **继续保持"用完就卸"**（现状）：改动最小，且已经能用——峰 332 MB、稳态 71 MB。
  否决原因：峰值仍然违反口径，而且它出现在用户只是"点了一下朗读"的时刻；
  更关键的是 TTS 崩溃会连累整个应用，而朗读对核心取词功能没有任何依赖。
- **单独做一个 `lemma-tts.exe`**：隔离更彻底，甚至可以独立升级。否决原因：
  多一个要签名、要版本对齐、可能被漏打包的产物；而"同 exe 不同模式"已经能拿到
  相同的隔离收益（独立的进程地址空间）。
- **用 WASM / 纯 Rust 推理（如 `candle`）替代 onnxruntime**：理论上能把模型内存管得更细。
  否决原因：重写推理后端的工作量与风险远超收益，而且 Kokoro 的 ONNX 图能否被其它后端完整支持未验证。
- **把模型换成更小的**（如更激进的量化 int8/q4）：能直接降峰值。
  否决原因：会牺牲音质，而音质目前恰恰是用户唯一反馈的短板（"字字断开"）。
  等韵律问题解决、有音质基线之后再单独评估量化档位。

## Acceptance criteria

- 朗读前后主进程 RSS 增量 **< 20 MB**（模型完全在子进程里）。
- 子进程空闲 60 s 后自动退出，且退出后系统里不残留 `lemma.exe --tts-worker`。
- 朗读失败（子进程崩溃、模型缺失）时，主进程只报错、不崩，且下次朗读能重新拉起。
- `lemma.exe --tts-worker` 可被独立驱动（脚本喂 JSON → 得到 WAV 路径），便于无头验证。
- 连续朗读 3 句时，第二句起不再付 1.2 s 加载成本（worker 仍在）。

## Risks

- 管道 JSON 需要严格的版本/字段校验；worker 与主进程是同一个二进制，不会漂移，但仍要防脏数据。
- 子进程继承环境变量与工作目录，需要显式设定（尤其 `%APPDATA%` 相关路径不要依赖 cwd）。
- Windows 上 GUI 子系统程序的 stdin/stdout 管道可用，但**必须实测**（这是本方案最大未知数）。
- 若用户同时触发两次朗读，需要"打断前一次"的语义（现在是 `PlaySound` 打断，子进程侧要能复用）。
- 退出清理：主进程被强杀时子进程可能残留，需要 worker 自己检测父进程消失（或设空闲超时兜底）。
