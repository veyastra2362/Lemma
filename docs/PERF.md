# 性能基线与口径

> 本文件记录**实测**数据，不记录设想值。每次有实质变化就追加一行。

## 1. 口径定义（报数字必须带口径）

| 指标 | 定义 | 为什么容易骗人 |
| --- | --- | --- |
| `cold_start_ms` | 进程启动 → 托盘就绪，取自应用自己写的 `startup tray-ready Nms` 日志 | 不含安装器/系统预热的差异；机器冷热差异可达 50% |
| `rss_main_mb` | `lemma.exe` 主进程工作集 | **只算主进程**，这是"30–60MB"这类说法的常见来源 |
| `rss_tree_mb` | 主进程 + 全部后代进程的工作集之和 | 共享页会被**重复计入**，因此偏高 |
| `private_tree_mb` | 主进程 + 后代进程的私有提交之和 | 最接近"这块应用真占了多少"，推荐对外报这个 |
| `hud_first_paint_ms` | 热键 → 前端 `requestAnimationFrame` 里回报首帧 | Rust 侧 `show()` 返回只代表窗口系统收到请求，离出图还差一次合成 |
| OCR / TTS 延迟 | 必须区分冷启动（含模型加载）与热态（复用 session） | 混在一起报没有意义 |

## 2. 测量方法

```powershell
# 冷启动 + 内存（会启动真实窗口，6 秒后自动退出）
pwsh -File scripts/perf-baseline.ps1

# 「热键 → 首帧」需要真实按键，数据由界面右上角 / 设置页展示，
# 同时写进日志：perf hud-first-paint 22.3ms seq=1
```

产物落在 `.metrics/baseline-<时间戳>.json`，可以拿去对比。

### 3.2 由此得到的两条结论

1. **「常驻 30–60 MB」只能指 Rust 主进程**（实测工作集 27–29 MB、私有 6.3 MB）。
   整个进程树私有内存 ≈ 166 MB，其中 96% 是 WebView2 的浏览器/渲染/GPU/网络进程。
   任何对外口径都必须写清是哪一个。
2. **Rust 侧本身极轻**：主进程私有内存 6.3 MB。后续 OCR/TTS 的模型权重才是内存大头，
   这也是为什么计划里坚持"模型不常驻 + 空闲卸载"。

### 3.3 一次真实的优化：三窗口懒创建

初版把三个窗口都在启动时创建 → 三个 WebView2 渲染进程。

| 指标 | 三窗口启动创建 | 改 `"create": false` 后 | 变化 |
| --- | --- | --- | --- |
| 冷启动 | 805.7 ms | 549.8 ms | **−32%** |
| 主进程工作集 | 32.9 MB | 27.0 MB | −18% |
| 进程树工作集 | 483.7 MB | 347.8 MB | **−28%** |

改法：`tauri.conf.json` 里 settings / ocr-region 声明保留（路由与透明配置依赖声明），
但加 `"create": false`，由 `core::shell::ensure_window()` 在用的时候按配置构建。

## 3.4 M3 之后的内存变化（2026-11-04）

功能增加带来了两处常驻内存变化，**不是退化，是新增能力的成本**，必须分开记：

| 来源 | 增量 | 何时付出 | 口径 |
| --- | --- | --- | --- |
| 翻译层（reqwest + rustls） | 主进程 RSS **28.4 → 35.8 MB**（+7.4 MB） | 启动后预热连接即常驻 | 含 TLS 会话、连接池、证书链 |
| 中文分词器（**优化后**） | 峰值工作集 9.4 → **7.5 MB**（无可测增量） | **懒加载**：第一次遇到中文取词时 | 从侧文件 `zh-words.txt` 顺序读，不碰 redb 中文表 |
| ~~中文分词器（优化前）~~ | ~~7.4 → 35.7 MB（+28 MB）~~ | 同上 | 遍历 redb 中文表把整张表的页带进了工作集 |

**优化前的 28 MB 里，词表结构只占 4–5 MB，大头是遍历 redb 中文表时被 mmap 带进工作集的页。**
改法：导入 CC-CEDICT 时另存一份 `zh-words.txt`（每行一词，1.03 MB），分词器顺序读它。
实测：加载 79 ms → **20 ms**，峰值工作集 35.7 MB → **7.5 MB**（与只查词的 9.4 MB 同量级）。

**踩到的坑**：第一版仍然走了 redb 回退路径——因为导入时 `redb` 的 `Database` 直到 drop 才落盘，
词库 mtime 反而晚于侧文件，新鲜度校验判定"过期"。修法是**先 `drop(store)` 再写侧文件**。

剩余优化方向：翻译层若长期不用可考虑空闲后 drop 连接池（收益待测）。

## 2\.9 UI v2 之后的开销复核（2026-11-05）

UI 重做（石墨令牌层 + 设置左导航 + 对照窗口重排）之后复核一遍，确认没有把性能做坏。

口径：同机、同 release 产物、每次运行前杀掉进程；冷启动取**应用自报**的
`startup tray-ready`（不含后续预热），HUD 首帧取**前端 rAF 回报**的
`perf hud-first-paint`，都用真实双击 Ctrl 触发（冒烟入口在 WebView 尚未挂载时触发，
拿不到首帧回报）。

| 指标 | UI v2（中位） | 重做前 | 差 |
| --- | --- | --- | --- |
| 冷启动到托盘就绪 | **575 ms**（566 / 575 / 783） | 634 ms | −59 ms |
| HUD 首帧 | **16.2 ms**（13.5 / 16.2 / 22.5） | 15–27 ms | 持平 |
| Rust 主进程工作集 | **36.5 MB** | 36.4 MB | +0.1 MB |
| 进程树私有内存 | **170.1 MB** | 172.2 MB | −2.1 MB |
| 进程数 | 7 | 7 | — |

**单次采样会骗人**：第一次跑基线脚本时读到 816 ms 冷启动，看着像回归 +181 ms；
连跑三次才发现那是冷缓存噪声，中位数反而比改前更快。
所有启动/首帧数字必须**多次取中位**，单次不作为结论。

## 3\.5朗读（TTS）的内存：已隔离到子进程

| 场景 | 主进程 RSS |
| --- | --- |
| 朗读前（只有词库 + 翻译层 + WebView2） | 30 MB |
| 加载 Kokoro 中文 q8 模型后 | **332 MB** |
| `release_model()` 卸掉会话 800 ms 后 | **71 MB** |
| 稳态残留 | 约 41 MB（`ort` 的分配器保留，不还给系统） |

**最终实现（子进程隔离，2026-11-04）**：

| 场景 | 主进程 RSS | worker RSS |
| --- | --- | --- |
| 朗读前 | 30 MB | — |
| 第一次朗读（含拉起 worker 与加载模型） | **44 MB（+14 MB）** | 约 245–305 MB |
| 空闲 60 s 后 | 44 MB | 已回收（进程消失） |

对照：进程内路径（`LEMMA_TTS_INPROC=1`）峰值 333 MB。

结论：
1. **TTS 必须在主进程之外**——模型权重是 300 MB 量级的物理事实，不是优化能解决的。
2. 切分点在**音素边界**：拼音要查被主进程独占加锁的 redb，子进程打不开。
3. 空闲回收必须靠**独立线程**：只在"下次朗读"时检查等于不回收。

## 4. 测量时的坑

- **裸 `cargo build --release` 得到的不是生产形态**：`tauri-build` 仍会置 `cfg(dev)`，
  应用会去加载 `http://localhost:1420`，跑起来是白屏。必须用 `pnpm tauri build`。
- 同一台机器上若开着其它 WebView2 应用，按进程名统计会串味；本脚本按**父子树**统计。
- 工作集之和会重复计入共享页（DLL、字体、共享内存），所以 `rss_tree` 明显高于 `private_tree`。
- `cold_start_ms` 在第一、二次运行之间差异较大（首次有文件系统缓存冷启动），
  取多次中位数更可靠。
- HUD 预热窗口停在屏幕外时，WebView2 可能挂起渲染，因此"首次呼出 22 ms"里仍含一次页面加载；
  真正的纯热态是 5 ms。
